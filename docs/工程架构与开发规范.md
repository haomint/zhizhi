# 知枝：工程架构与开发规范

基线日期：2026-10-24。当前正式版本：1.1.0。本文记录实际完成的 TS/React 结构，替代此前候选技术栈和未落地目录建议。

## 运行与仓库

前端和本地业务层在同一个私有 Git 仓库。正式应用目录继续使用 `outputs/learning-grove/`，保持现有 Android 构建、交付位置与托管预览的关联。MVP 没有必须远程部署的业务服务器：Agent、工具和数据在手机内，模型推理与可选资料检索联网。

主要应用源码使用 TypeScript / TSX，界面使用 React。必要的 Android 系统能力由现有 Java 插件完成；Python 只保留工程构建/预览兼容工具与明确归档的旧实现，退出正式学习业务路径。

## 职责边界

| 模块 | 路径（相对正式应用目录） | 职责 |
| --- | --- | --- |
| 界面 | `src/ui/`、`src/main.tsx` | React 页面、表单、阅读、导航、进度展示 |
| 契约 | `src/contracts.ts` | 动作、状态、档案、模型阶段及接口类型 |
| 应用服务 | `src/application/service.ts` | 排队、取消、阶段协调、版本冲突与原子提交 |
| 业务核心 | `src/core/` | 学习生成、记忆、结算、加强、路线、Pi 与结果校验 |
| 平台适配 | `src/platform/`、`android/` | IndexedDB、加密 Key、模型网络、资料检索与系统分享 |
| 教学规则 | `skills/` | 流程与学科规则；构建时同步资源 |

UI 使用类型化 `Action` 调用 `LearningService.dispatch()`，通过 `read()` 与 `subscribe()` 获取 `Snapshot`。模型与工具不直接保存档案；成功结果通过服务层提交后才反映到 UI。业务层不依赖 DOM，不覆盖全局 `fetch`。平台接口和 Repository 可替换，测试注入模拟网络与独立 IndexedDB。

## 功能基线

MVP 保持八类能力：明确学习需求、学习路线、资料来源、卡片式学习、主动答疑、反馈与个人记忆、知识树与自愿加强、保存与失败恢复。账号/云同步、多人学习、大型全学科知识库、多 Agent 调度和通用 Skill 自动升级继续后置。

主线讲述与完整例子；加强学习自愿进入；阅读状态不等于掌握。核心依据不足不发布，重大路线修改经用户确认，失败和取消保留已提交内容。

## 数据与升级

- 维持 `zhizhi-app` 数据库、`state` store、`document` key 与档案格式 `zhizhi-personal-2`。
- 维持应用 ID `app.zhizhi.personal.v1`；1.1 的 versionCode 6 高于 1.0.1 的 5，并复用 v1 签名。
- 签名与资源一致性由脚本核对；真机覆盖安装与生命周期需设备验收。
- 生成任务与短写入分开；版本变化拒绝旧结果；取消不发布半成品；事件结算去重。
- 记忆纠正/遗忘保留证据关联；档案合并映射 ID，替换保留恢复点；密钥不进入档案。

## 开发与检查

Node.js 24+，依赖版本由 package-lock 固定。`npm run dev` 开发，`npm run check` 执行格式、37 项回归、严格类型检查、构建和工程核对，GitHub Actions（`.github/workflows/check.yml`）在每个 PR 上执行同一检查；`.github/workflows/pr-guard.yml` 另按固定规则检查 PR 描述与改动是否一致、测试是否减少或被跳过、是否新增密钥。新业务使用 TS，React 组件使用 TSX；禁用通过 `any`、`@ts-ignore` 或 `@ts-nocheck` 绕过检查的做法，由 `tests/architecture.test.mjs` 检查。外部 JSON 仍必须在运行时验证。

上表的依赖方向由 `tests/architecture.test.mjs` 强制：`ui/` 只经应用服务工作，`core/` 只依赖契约且不使用浏览器全局对象，`platform/` 只读取 `core/domain.ts`。仓库使用 LF 换行（`.gitattributes`），Windows 检出同样通过格式检查。AI 编程助手的规则入口为根目录 `AGENTS.md`。

每个任务用「任务」模板开 Issue 写验收条件，由成员认领（AI agent 不认领，只做认领人交给它的任务），再按 `类型/编号-简述` 建分支实现和验证，提交说明改变了什么及其依据。PR 记录相关测试和待验证项，合入 `main` 需要 `web`、`guard` 检查通过并处理代码审查讨论，不强制批准人数；认领、审核与避免冲突的细则见 `AGENTS.md`「多人协作」。多人使用独立工作目录/worktree。源码回退与数据回退分别处理；API Key、签名、数据库、缓存和安装包排除于 Git。

PR 由 CI/PR Guard 执行工程与固定规则检查，Codex GitHub 机器人独立查错；项目 skill `.agents/skills/zhizhi-review/SKILL.md` 只核对 Issue 验收条件与证据。标准见根目录 `REVIEW.md`，接入与操作见 `docs/PR审查与验收.md`。审查员每发一次意见算一轮，最多三轮，第二轮起只看新改动；意见回复“已修改”或“不修改及理由”，仍有实际问题时重新设计或拆小 PR。合并人确认当前提交的 CI、Guard、机器人结果和人工验收；作者自查不能代替机器人结果。
