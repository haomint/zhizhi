# 知枝：内容生成与逻辑优化实施指导

版本：0.2｜日期：2026-10-23｜状态：可用于拆分开发任务与编写规则的设计基线，尚未在应用中实现。0.2 同步分批生成、有限检索、较宽调整权限和学习结算的讨论结论。

版本衔接：当前统一基线见[《知枝-MVP完整策划案》v3.0](/workspace/三创赛知枝/outputs/知枝-MVP完整策划案.md)。Pi 最小验证及后续实施顺序以新版为准；本文件保留专项数据和方法细节。

## 先读这一页

**目标：生成对本次学习有用、依据可追溯、讲解连贯的内容，并让具体反馈改善后续教学。** 本轮只规定内容与内部逻辑；界面、动画、知识树美术和安装包不在范围内。

采用一个学习主 Agent，复用已完成独立最小验证的 Pi Agent Core 路径。程序决定阶段、提供上下文、校验与保存；模型负责整理知识、安排教学、编写和提出修订。多个生成步骤不等于多个 Agent，正式内容业务尚未接入。

核心生成链：

> 学习约定 → 节点学习价值与前置关系 → 资料和知识要点 → 节点页序 → 卡片正文 → 质量检查 → 保存近期内容。

核心改进链：

> 用户主动反馈 → 找出具体问题 → 局部修正 → 更新相关教学记录 → 后续生成采用；通用规则另外评估发版。

已经确定的规则：先定义与诠释，再按需安排例子、区分、用途和拓展；节点主标题稳定；每页只推进一个小目标；主线讲述和举例、不强制作答、不自评掌握；加强学习独立且由用户主动选择。

开发时优先打通一个完整节点，不一次生成整门课。下文带“建议默认”的细节用于验证，不写成已验证的效果结论。第 9 节记录已接受方向与仍待讨论的取舍；全局线路及待定项以《知枝-全流程逻辑与决策总览》为入口。

## 1. 每个节点先回答四个问题

在写卡片前生成 node_brief，作为内容取舍与验收锚点：

| 项目 | 要写清什么 | 作用 |
| --- | --- | --- |
| 学习价值 | 这个节点帮助当前用户理解或完成什么 | 防止经典术语堆砌 |
| 学习目标 | 本次只需了解、解释、计算还是应用；具体到可观察表现 | 决定深度，不等于强制测评 |
| 前置关系 | 需要哪些概念，其中哪些已经讲过，哪些理解仍未知 | 避免跳步和循环依赖 |
| 范围边界 | 必须讲什么、暂不深入什么、后续哪里会用到 | 控制展开与衔接 |

节点缺少学习价值时，先移到候选列表，不因为“重要”“经典”就直接加入主线。发现关键前置缺口时，先考虑一句回顾或一张补充卡，确实改变路线时再提出框架修订。

## 2. 生成分为五步，留下可检查的中间结果

| 步骤 | 输入 | 输出 | 进入下一步的条件 |
| --- | --- | --- | --- |
| A. 确定节点任务 | 学习约定、框架、相关记录 | node_brief | 学习价值、目标、前置和边界明确 |
| B. 整理知识依据 | 节点任务、可用材料和检索结果 | knowledge_notes | 必要知识要点、来源状态、疑问有记录 |
| C. 编排教学 | 知识要点、相关偏好、前后节点 | card_plan | 必要内容有位置，顺序合理，无未处理的关键跳步 |
| D. 编写卡片 | 页序、知识要点、例子要求 | cards_draft | 正文与计划对应，案例和计算完整 |
| E. 检查与提交 | 草稿、材料、学习约定 | review_result 与可发布版本 | 结构有效，无未处理的阻塞问题，保存成功 |

这些是逻辑步骤，不要求固定五次模型调用。MVP 可以将 A+B、C+D 适当合并；但输出里仍能辨认各步骤的结果，便于定位错误。

资料检索与框架允许局部往返。关键材料不足时，优先调整相关节点或提出缺口，不从头重做全部访谈。

### 2.1 知识依据不能只保存链接

knowledge_notes 至少记录要点、性质、材料引用与位置、资料实际支持什么、仍未确定什么。性质可区分定义、事实、推导、解释、争议与教学例子。

来源至少区分：

- material_supported：已读取的指定材料支持该要点，不等于独立核验。
- corroborated：完成了有记录的比对或验证，说明验证方式和范围。
- model_generated：基于模型生成，尚无已读取材料支持。
- unresolved：资料缺失、关键冲突或无法确定。

模型自行报出的出处不能直接变成已读取来源。工具或程序登记材料 ID 和读取位置，再供模型引用。检索不可用时如实标记，不用看起来正式的 URL 填空。

原创教学例子可自行构造，但必须标记为虚构或简化情境，说明假设，并检查它与所讲概念是否一致。它不能充当现实事实的证据。

### 2.2 页序计划与卡片正文

概念型节点默认覆盖定义与白话诠释、典型例子、必要区分与边界、用途与相关拓展、收束与衔接。环节不等于固定张数，简单可合并，复杂可拆开。

程序型节点可以按步骤与原理编排；历史专题按背景、事件、证据、因果等编排。通用流程配合学科规则，不能把所有学科写成同一套模板。

card_plan 说明每页小目标、要用的知识要点、例子和前后连接。卡片正文不能另行改变节点目标或引入与约定无关的大段拓展。

## 3. 七项内容质量检查

| 检查项 | 检查问题 | 不通过时处理 |
| --- | --- | --- |
| 有用 | 是否服务本次目标，为什么现在学 | 缩减、移到支线或调整节点位置 |
| 有据 | 关键结论由什么支持，是否如实标注不确定 | 补资料、限定结论或标记待补 |
| 准确 | 定义、条件、符号、单位、计算和结论是否一致 | 修正错误，必要时重新核对依据 |
| 前置充分 | 有没有用到未解释且不可缺少的概念 | 简短解释、补卡或提出前置节点 |
| 例子有效 | 是否对应定义，是否暗中增加假设，类比边界是否说明 | 重写例子，增加必要条件 |
| 深度合适 | 是否过浅、推导过重、重复或无关扩展 | 调整内容，保留必要严谨条件 |
| 连贯 | 页间、节点间能否接上，旧例子是否被正确承接 | 调整顺序和连接语，消除冲突 |

不使用没有验证依据的综合分数。review_result 保存具体问题、对应卡片、依据与处理动作。

问题分两类：blocking（错误、关键条件遗漏、必要依据缺失、计划有关键断层）与 improvement（可读性、例子选择、局部冗余）。先处理阻塞问题；不要为追求文案完美无限重写。

程序检查 ID、字段、引用存在性、页序和计算一致性等可执行项；模型配合材料检查语义与教学完整性。模型自查或另一次审查不能证明全部正确。没有充分依据时保留不确定，不能把审查通过写成事实核验完成。

建议默认：一次生成任务最多自动修订一轮；仍有阻塞时保存草稿和问题，等待补资料或用户选择。不把失败草稿混进正式内容，既有内容保持可读。

### 3.1 已接受的暂行方案：有限检索与滚动生成

整体路线先有轮廓，当前节点细化，远期节点保留目标与资料缺口。检索以节点必须回答的问题为边界，核心要点有依据、必要条件明确、例子自洽且无阻塞冲突时停止，不以资料数量充足作为成功标准。

缺失的非必要拓展可推迟；不确定细节可核实或删去；核心定义或结论缺依据则暂缓该部分；合理的不同解释保留分歧，不强行拼成确定结论。缩小范围可以，猜测补核心结论不可以。

用户明确同意采用：首批准备一个完整小节点，经检查保存后开始学习，随后持续准备下一节点；更远节点先规划，不提前生成大量正文。节点是质量单位，批次是运行安排。第一版以“当前节点＋下一节点”为储备方向，实际数量按等待、重写和质量问题调整，不承诺固定秒数或页数。

生成任务与翻页、位置保存分离，网络请求不长期占用全局写锁。优先当前提问、主动打开的缺内容节点，再做后续备课。结果写入核对约定、节点与适配版本，过时结果不覆盖新安排。安卓后台持续生成仍未实现，不能以“滚动准备”暗示后台执行已获保障。

## 4. 个性化：每条记录要能解释它改变什么

| 反馈 | 解释与动作 | 适用范围 |
| --- | --- | --- |
| 先说是什么 | 新概念先建立定义与含义，再展开 | 本次学习；长期沿用需有对应依据 |
| 数字作为例子 | 先讲用途，计算用来解释概念，不默认长推导 | 当前任务或学科情境 |
| 多补基础 | 定位缺少的前置内容，补必要知识，不机械加字数 | 相关节点 |
| 这个例子不懂 | 区分陌生情境、术语困难或推理跳步，再换解释 | 先当前卡片，后相关未生成内容 |
| 太简单 | 减少重复，按目标增加深度或应用 | 不直接写“已掌握” |
| 不要频繁提问 | 讲述和完整例子为主，主动提问入口保留 | 当前项目已选定的默认主线方式 |

每条适配记录保存：用户原话/事件引用、记录性质、范围、生成动作、更新时间与有效状态。无法对应具体生成行为的空泛标签，如“视觉型学习者”，不作为强约束。

本次明确要求优先于相关旧偏好；不同学科情境可以并存；用户纠正后旧记录停止在该范围内生效。未反馈的效果记为 unknown，不把安静阅读或翻页速度视为接受、喜欢或掌握。

目标或范围改变要修订学习约定；表达偏好改变通常只需更新适配记录，不迫使用户重新确认全部访谈。

## 5. 连续性：除了学过什么，还要记住怎么讲过

每个节点完成或出现重要反馈时，更新简短 teaching_continuity：已介绍的关键概念、可复用的例子及适用条件、明确的困难或疑问、尝试过的解释、后续在哪个节点可能用到。

- 记录“讲过”，与“用户理解”分别保存；主线浏览只更新阅读事实。
- 问题被回应不等于已经解决；用户明确反馈解决，或后续相关表现提供证据时，再更新状态。
- 后续生成只读取与当前节点相关的线索，不反复发送全量历史。
- 引用旧交流带内部来源关联；找不到记录时不虚构共同经历。
- 避免给每个节点重复完整旧例子，可以简短回扣；新旧条件不同时明确差异。

“越来越适合用户”先体现为更少重复、更少跳步、正确使用偏好与相关经历。学习收益仍需实际观察，不能用记忆条目数量代替。

## 6. 两类优化循环

### 学习中的内容调整

保存主动反馈 → 识别问题类型 → 选择最小修改范围 → 生成修订 → 检查保存 → 后续相关生成沿用。

已接受方向：赋予 AI 较宽的教学调整权限，在严谨与适用约束下直接优化讲解和后续内容。补前置、局部重排和推迟拓展等调整可主动进行，路线变化让用户简短知情，保留原因与可撤回版本。改变原始目的、转向另一主题或大幅扩大负担时，仍先给出建议让用户选择；幅度的具体划分需用案例细化，不把所有局部改动变成审批。

已读正文不因偏好变化批量覆盖；用户要求重写则保存新内容版本与关联。发现明确事实错误属于纠错，应保留修订记录，并让错误内容停止作为后续依据；不能以“保留旧版”为由继续传播。

### 每次学习后的结算与个人策略

用户认可按一次连续学习活动整理：本次经历、讲过的概念与例子、疑问和反馈、可执行的个人教学策略。明确反馈当场生效，结算再做归纳去重；结算不要求用户额外填写总结。

记录及时保存，结算可以延后。用户明确结束时结算；中断时保存待处理任务，下次运行补做，不依赖关闭应用瞬间完成网络请求。结算只处理本次新增范围并引用上次摘要，需可去重和追溯；会话切分与失败重试细节尚待定。

跨学科承接采用“结算整理索引、生成前检索相关经历”。过去学过高数不等于所有相关能力都已掌握；只有实际记录支持且有助于当前理解时才引入旧概念或例子。无反馈时不推定策略已有效。

### 通用 skill 迭代

将可复现问题登记为 improvement_case：输入情境、旧规则版本、旧输出、预期行为、问题归属、候选改动。先判断是事实材料、个体偏好、上下文不足、偶发输出，还是通用规则漏洞。

个体偏好优先存入适配记录，事实错误先修内容与依据；通用漏洞才修改正式 skill。以固定案例比较修改前后，检查原问题、其他场景与调用代价，再发布带说明的版本。建议默认由项目负责人验收通用规则版本，不在每次使用后自动改写正式规则；自动化程度待第 9 节决定。

## 7. Pi 单 Agent 与现有项目怎样落地

本文是知枝业务设计，不声明 Pi 自带这些字段或教学策略。Agent Core 已有独立最小实现与用户通过反馈，正式业务、资料与记忆契约仍需增量接入验收，不能把最小验证扩大为完整系统通过。

| 层次 | 具体工作 |
| --- | --- |
| 通用流程规则 | 节点任务、知识整理、页序、编写、检查、反馈归因 |
| 学科规则 | 数学的条件与推导、历史的证据与解释等，不复制整套通用流程 |
| 教学方法 | 例子、比较、分步解释等按目标选择 |
| 业务程序 | 稳定 ID、版本、状态推进、校验、去重、保存、上下文筛选 |
| Pi 适配 | 复用模型与工具循环；每次只提供当前阶段需要的规则、材料和工具 |

先为各步骤定义输入输出，再接运行内核。节点草稿、审查和卡片版本作为业务记录保存，不依赖无限增长的 Agent 会话。

知识整理可用现有检索或材料读取工具；没有工具时，允许使用已提供材料并如实标注能力缺口。模型适配、工具协议和安卓兼容须实际验证，本文不等于已完成 Pi 集成。

当前 skills/cards.md 仍固定三张、含思考问题；本方案与其存在明确差异，实际实现时必须同步调整提示词、结果校验及按需生成逻辑，不能只改文案。本次不改代码，不引入 UI 工作。

建议最小交接对象：

```json
{
  "schema_version": "content-1",
  "agreement_revision": 1,
  "node_id": "node-example",
  "node_revision": 1,
  "node_brief_ref": "brief-example",
  "knowledge_notes_ref": "notes-example",
  "card_plan_ref": "plan-example",
  "cards_revision": 1,
  "source_status": "material_supported",
  "review_status": "draft",
  "blocking_issues": [],
  "adaptation_refs": [],
  "continuity_refs": [],
  "rule_versions": {"content_pipeline": "0.1"}
}
```

示例 ID 均为占位，并非已有数据库记录。source_status 是便于查看的汇总，具体要点仍各自保留来源状态，不能用一个已核验材料掩盖整节点的未知。review_status 为 draft / needs_revision / ready；程序仅在所选资料策略允许、无阻塞问题、保存成功时设置 ready。

## 8. 怎样验收第一版

先用一个小节点跑完整生成链，检查所有中间结果；再用用户主动反馈观察下一次生成是否变化；最后换学科验证通用规则是否过度模板化。

固定案例至少包含：

1. 新概念：定义、例子、边界都正确衔接，没有用类比代替定义。
2. 前置不足：能补关键解释，不假装用户已经掌握。
3. 例子难懂：修改原因清楚，相关后续内容采用新安排。
4. 资料缺失或冲突：如实保留状态，不编引用，按资料策略处理。
5. 用户改变情境偏好：只更新相关范围，旧冲突信息不继续生效。
6. 已学内容接续：引用实际讲过的概念或例子，不虚构用户理解。
7. 数学与历史各一例：遵守各自内容要求，不全部写成固定概念三张卡。
8. 用户不回答知识问题：主线仍能完整阅读，无默认测验，不判定不积极。
9. 格式错误或保存失败：草稿不伪报正式内容，不破坏已提交版本。

验收看可定位的问题、修订理由及输出，不只看 JSON 是否能解析。以上为待执行案例，本轮只完成文件与示例格式检查，不宣称内容质量或学习效果已通过验证。
