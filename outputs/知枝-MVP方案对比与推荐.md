# 知枝：MVP 方案对比与推荐

评估日期：2026-10-23。依据引用会话、当前会话、项目现有说明和部分源码，以及 Pi 官方文档。讨论归档见[《知枝-讨论总结与决策记录》](/workspace/三创赛知枝/outputs/知枝-讨论总结与决策记录.md)。

建议采用的组合是：一个学习主 Agent，优先验证 Pi Agent Core；知枝保留薄的业务控制与数据层；skills 采用通用流程、学科规则和教学方法组合；教学围绕目标和学习事件调整；记忆随使用更新，通用规则经案例验证后再发版。

这是一份设计推荐，不是已实施方案。Pi Core 的选择以安卓兼容验证通过为前提；如果部署方式改成 Node/Bun 服务，完整 SDK 的优先级会提高。

**一、两轮讨论各自更有价值的部分**

两轮讨论处理的是不同层次，适合组合，不必整套选一套。

| 比较项 | 引用会话的贡献 | 本轮讨论的贡献 | 我的取舍与原因 |
| --- | --- | --- | --- |
| 教学流程 | 学习约定、节点目标、事件触发、局部调整 | 说明由单 Agent 承载这些能力 | 保留引用会话的流程定义，用本轮架构执行；运行框架本身不决定教学质量 |
| 需求访谈 | 模拟暴露漏答、多选侧重、自评不充分等真实问题 | 提出学科和目标影响教学方式 | 优先采用模拟后的访谈规则；有具体失败案例，容易验收 |
| 通用运行机制 | 偏向程序调度现有四类模型调用 | 引入 Pi 以复用 Agent 循环 | 倾向复用 Pi，但让程序继续约束合法动作与提交边界；两者职责可兼容 |
| Agent 数量 | 不必引入多个 Agent | 明确从总/子 Agent 收敛到单主 Agent | MVP 只做一个；当前任务关联紧密，拆分尚无明确收益 |
| 学科差异 | 强调按目标、资料和反馈调整 | 提出三层规则组合与跨学科节点 | 采用本轮设计；比每门学科复制一套完整流程更易维护 |
| 记忆 | 来源、证据、情境、纠正与删除 | 强调记忆独立于会话，复用统一工具 | 合并采用；独立存储解决可靠性，证据与范围解决正确使用 |
| skill 优化 | 分清局部调整、个人适配、通用规则迭代 | 明确维护任务也可复用相同运行内核 | 采用引用会话的版本迭代规则；无需为维护单独建立常驻 Agent |
| 开发节奏 | 小主题完整流程，每轮增强后重跑 | 先验证运行内核与跨学科适配 | 合并为先做技术验证，再做完整学习验收；避免分别成功却无法衔接 |

引用会话在“用户反馈如何变成教学动作”上更完整，本轮在“如何复用运行机制与组织不同学科能力”上更清晰。最值得保留的是这两组内容的组合。

**二、运行框架：Pi Core、完整 SDK 与现有调用方式**

评估前提是现有安卓独立运行要求。按源码，界面通过本地业务层和原生网络插件调用模型，资料主要保存在 IndexedDB，密钥由安卓系统加密保存。

| 方案 | 优点 | 需要承担的工作 | 适用判断 |
| --- | --- | --- | --- |
| 继续现有按阶段调用 | 改动最小，可保留当前产品基线 | 扩展自主工具循环时仍需新增通用机制 | 适合作为迁移前的对照基线与未通过验证时的保留路径 |
| Pi Agent Core | 复用 Agent 状态、工具执行循环与事件流，知枝可自行组织上下文与业务工具 | skills 加载、持久化、上下文策略、移动端模型通道和任务恢复仍需接入 | 当前优先做验证的候选 |
| 完整 Pi SDK | 已有更多会话、压缩、资源加载和扩展机制 | 官方嵌入在 Node/Bun；当前安卓架构需要额外运行环境或部署变化，并协调数据职责 | 接受 Node/Bun 服务后更值得优先采用 |

Core 的能力边界见[官方 Agent 文档](https://github.com/earendil-works/pi/blob/main/packages/agent/README.md)。完整 SDK 的运行环境及会话、资源配置能力见[官方 SDK 文档](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/sdk.md)。

推荐 Core 是基于当前部署约束的工程判断，不代表 Core 在所有项目中更省工。若最终需要自行重建大量 SDK 已有能力，应重新比较维护成本。

需要修正前面讨论中容易造成的误解：Agent Core 不包含完整 SDK 的 skills 与插件加载；也不能仅把现有 native.generate 接口接上，就视为 Agent 工具循环打通。本次查看的 Java 请求只发送 system/user 文本、关闭流式输出，并只提取回复正文；还没有传递工具调用所需的完整消息结构。

因此，技术验证至少覆盖：

1. 在实际 Capacitor 构建与 Android WebView 中验证依赖及运行方式，确认不依赖未提供的 Node 能力。
2. 在不将密钥暴露给普通网页脚本的前提下，验证模型请求通道。原生桥接若继续使用，需要支持工具定义、调用、结果及相关错误，而非仅传输正文。
3. 验证一次“模型请求工具 → 执行业务工具 → 回传结果 → 模型完成回答”的完整循环。
4. 验证超时、用户离开页面、取消或重试时的状态；设置轮次与工具调用上限，达到上限后保存可解释的停止原因。
5. 验证学习状态持久化，以及重开后从已提交状态继续。MVP 可以中断任务并允许重试，不必承诺后台持续执行或任意断点恢复。

以上是后续验收要求，本次没有执行。验证不通过时，先保留现有阶段调用并定位适配成本，不应悄悄把手机独立运行改成必须依赖自建服务。

**三、Agent 组织：单主 Agent 优先**

| 方案 | 主要收益 | 主要成本 | MVP 评价 |
| --- | --- | --- | --- |
| 单 Agent，多 skills 与工具 | 同一学习目标内上下文连贯，排查和记忆管理较直接 | 需要控制上下文和任务边界 | 推荐实现 |
| 总 Agent 协调多个子 Agent | 可委派独立、耗时或需要隔离上下文的任务 | 任务分派、信息传递、结果合并、失败恢复和并发写入 | 有实际需要后再增加 |
| 每门学科一个 Agent | 角色配置可独立 | 跨学科衔接复杂，容易重复通用规则和记忆逻辑 | 目前优先用学科规则解决 |

“主 Agent”当前指负责与用户持续学习的 Agent，不意味着它要先具备总调度功能。规则评估、阶段总结可以用同一 Agent 定义在独立任务中运行，多次调用不等于必须建立多 Agent 系统。

未来出现后台备课、多个独立资料任务或有隔离要求的审核时，再评估委派。审核 Agent 也可能重复同一模型的错误，需要可靠资料与评价案例配合。

**四、业务控制：程序约束配合 Agent 判断**

| 设计 | 问题 | 推荐处理 |
| --- | --- | --- |
| 完全固定流水线 | 很难处理用户改变目的、跳读或临时困难 | 保留阶段骨架，允许由事件触发返回或分支 |
| Agent 自由修改全部状态 | 路线、记忆和正文容易缺乏可靠提交与追溯 | Agent 提出动作，程序验证作用范围、数据结构及当前版本 |
| 程序控制边界，Agent 判断教学动作 | 需要明确动作与工具契约 | 推荐；兼顾灵活性和可验证性 |

程序提供允许的工具和动作，负责稳定 ID、版本关联、写入校验、失败处理及持久化。Agent 负责理解反馈、选择讲解方式、生成内容，以及在允许范围内选择工具。Pi 复用的是模型和工具之间的执行循环。

不需要每次翻页都调用模型判断下一步。确定性操作直接执行；普通问题可在同一次生成中返回必要动作建议；涉及目标、路线或来源冲突时，再使用对应的处理规则。这样能控制等待和调用成本。

**五、skills：采用组合，避免重复和无限细分**

| 方案 | 长处 | 限制 | 判断 |
| --- | --- | --- | --- |
| 每个阶段只有一份通用 skill | 易起步 | 高数、历史等专业要求容易缺失 | 可作骨架，需要学科补充 |
| 每门学科复制整套 skills | 容易快速定制 | 通用规则重复，修改容易不同步 | 不推荐作为长期结构 |
| 每个知识点单独一份 skill | 个别主题可精细调整 | 数量膨胀，内容与教学方法混杂 | 只为反复需要的特殊方法细化 |
| 通用流程 + 学科规则 + 教学方法 | 共用流程，同时保留专业差异 | 需要明确选择规则与优先级 | 推荐 |

这里的三层是知枝自己的设计，不是 Pi 自动提供的教学编排。Pi 的 skills 是按需加载的指令及辅助文件，模型可能漏选；关键阶段需要由应用明确提供或调用相关规则。[Pi Skills 文档](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/skills.md)

每次任务建议显式提供：当前阶段、学习约定版本、节点及其目标、学科/主题、相关资料、用户表现、所需输出。skill 的设计说明则记录适用条件、输入、处理要求、输出、质量检查、异常出口和版本。它们是业务约定，不能仅靠提示词替代代码校验。

高数与历史的首批差异可以这样落地：

| 任务 | 高数 | 历史 |
| --- | --- | --- |
| 规划 | 标出函数、极限等前置关系，按目标决定是否包含证明 | 依据学习目的组合时间线、专题、因果与比较 |
| 生成 | 保留符号、定义条件、推导依据，区分直观与严格结论 | 保留时间、地点、背景和出处，区分史实与解释 |
| 检查 | 根据目标检查计算、解释、推导或应用 | 根据目标检查时序、证据使用和论证，不只检查背诵 |
| 记忆 | 记录具体易错步骤及证据 | 记录具体混淆的时序、因果或证据使用问题 |

例子、反例、分步示范和回忆练习按需选择。数学不必每次证明，历史也并非不需要记忆或数量分析。教学方法要服务于当前目标，不能变成学科刻板模板。

专业规则设计可参考[历史思维框架](https://historicalthinking.ca/historical-thinking-concepts)中的史料、因果和历史视角，以及[IES 教学指南](https://ies.ed.gov/ncee/wwc/PracticeGuide/1)中的示例与练习交替、具体与抽象表示等方法。这些资料支持部分教学原则，不构成对本项目三层架构效果的验证。

未覆盖的学科可先用通用规则与明确来源提供有限服务，标明资料和规则缺口，再通过案例补充，不让模型临时生成的学科规则直接成为正式标准。

**六、需求分析：采用模拟修正后的方案**

推荐“自由表达 → 关键缺口补问 → 暂定安排 → 体验验证”，比长问卷或缺什么都追问更适合当前产品。

原因来自引用会话的具体案例：交易经历不等于理论基础；多选且有侧重是有效信息；用户可能只回答复合问题的一部分。未答要留未知，不能强行归入某个程度，也不能推断为不积极。

访谈的启动条件是知道主要目的、预期程度，并有一个可调整的起点。漏答只有在影响下一步时才追问。界面允许选项加自由补充，多选可以标注侧重，“不确定，先体验”也是有效结果。

该规则应先应用在需求 skill 和交互逻辑上，不能只改变选项文案而仍要求所有字段填满。

**七、记忆与迭代：区分事实、判断和通用规则**

推荐“原始记录 + 有情境的个人资料 + 有证据的学习判断”。记忆独立于 Pi 会话保存，使用统一读写工具；Pi 会话上下文、学习树状态、长期记忆分别承担不同职责。

| 取舍 | 推荐 | 原因 |
| --- | --- | --- |
| 全量历史每次发送 / 选择相关信息 | 按当前目标、节点和问题检索 | 控制上下文，减少旧情境干扰 |
| 模型判断直接覆盖 / 候选更新后校验 | 校验来源、范围、重复和冲突后写入 | 避免一次答错形成永久标签 |
| 偏好立即改全局 skill / 偏好保存在个人资料 | 先个人适配 | 一个人的表达习惯不代表通用规则 |
| 每次对话自动改 skill / 版本化评估 | 问题记录、候选修改、案例验证、再发版 | 改动可归因、可回退 |

记忆至少记录内容、来源、适用范围、时间和状态；学习判断还要关联题目或原话。用户的新纠正与旧信息冲突时应保留替代关系；无来源时不虚构共同经历。已浏览和有掌握证据分开，不将翻页速度当作学习能力。

MVP 可先人工触发规则评估，用固定案例比较修改前后。事实错误先修内容与资料，个体偏好先修适配记录，能复现的通用漏洞才进入 skill 发版流程。

**八、开发节奏：整体骨架先行，完整学习过程逐轮验收**

一次性写满整套逻辑会积累未验证假设；逐模块做完再整合容易遗漏衔接。因此推荐以下顺序，作为后续开发建议：

| 顺序 | 产出 | 通过依据 |
| --- | --- | --- |
| 1. 保存基线，定义最小数据关联 | 可比较的现有行为、学习约定、节点目标、来源与事件字段 | 能解释生成输入、输出及写入位置；基线是否用 Git 保存需另行落实 |
| 2. Pi 移动端技术验证 | Core 与模型通道的一次完整工具循环 | 真正完成调用、结果回传和出错处理；不只在桌面 Node 中通过 |
| 3. 单主 Agent 的完整学习过程 | 从自由表达到卡片、一次答疑、记录与重开接续 | 用户反馈影响后续内容，失败不破坏已保存资料 |
| 4. 跨学科与交互案例 | 数学、历史、跨学科小主题 | 同一流程能遵守不同学科要求，未知信息和多选意图被保留 |
| 5. 来源与记忆增强 | 资料对应、纠正与检索 | 来源能追溯，纠正后的旧判断不继续使用 |
| 6. 规则版本迭代 | 修改说明与比较结果 | 原问题改善，其他典型案例无明显退化 |

首轮可使用人工选定的可靠资料，之后再接自动检索。现有独立安卓版本的真机使用、导入恢复和升级资料保护仍需推进；运行内核改造不能代替这些产品验收。

**九、建议保留的验收案例**

这些是建议案例，尚未执行；验收检查行为与结果，不仅检查 JSON 是否可解析。

| 案例 | 应观察到的行为 |
| --- | --- |
| 用户只回答学习经历，没回答基础 | 保存基础未知，选择可调整起点；不直接认定零基础 |
| 两种目标都选但有侧重 | 保留主次，路线体现优先级 |
| 只想了解导数 | 内容围绕变化率，不强制转成整套考试课程 |
| 用户说当前例子没看懂 | 先局部换讲解，下一次相关生成使用该反馈 |
| 历史解释缺少依据 | 保留待核实状态，不能生成虚假引文来填补 |
| 用户纠正学科偏好 | 只在适用范围内更新，旧判断停止作为有效依据 |
| 用户改目标 | 学习约定和相关路线修订，已读正文与旧问答仍可追溯 |
| 模型返回错误工具参数、网络中断或重试 | 校验并明确失败，保留已提交资料；重复写入有保护 |
| 重开应用继续学习 | 从已保存的位置与约定恢复，不将未提交任务伪报为完成 |

当前最值得先证明的是：同一个 Agent 在不同学科中，能够围绕同一份学习约定，根据实际证据调整下一步；运行、存储与失败边界可靠。子 Agent 和自动规则优化都应由明确的后续需求推动。
