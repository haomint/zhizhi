# 知枝：需求分析阶段实施指导（Pi 单 Agent）

版本：0.1｜日期：2026-10-23｜状态：设计基线，待实现与试用。

版本衔接：当前统一基线见[《知枝-MVP完整策划案》v3.0](/workspace/三创赛知枝/outputs/知枝-MVP完整策划案.md)。Pi 独立最小版已有实现与用户通过反馈；本文保留需求阶段细节，正式业务接入及其验证仍待实施。

本文将本会话的访谈模拟及其修正，与「pi轻量化框架可行性评估」会话合并，定义第一阶段怎么问、什么时候结束、交给下一阶段什么。本文不是已接入 Pi 的证明，也不是新安装的可执行 skill；本轮不修改应用代码。

## 1. 一页结论

**自由表达 → 提取已知信息 → 补问关键缺口 → 展示学习约定 → 进入框架草案与资料检查。**

- MVP 使用一个学习主 Agent，按阶段加载规则；不实现主从 Agent 调度。
- 复用已做独立最小验证的 Pi Agent Core 路径，接入正式需求业务。业务程序负责状态、校验、保存和阶段切换。
- 需求分析收集的是信息，不是要求用户逐题完成问卷。
- 每轮只问一个主要问题；可提供少量选项，始终接受自由表达。
- 漏答保持未知；多选保留主次；不确定可以先体验。
- 明确目的、范围和可执行的阶段成果，就足以准备下一阶段。基础与偏好不必全部确认。
- 用户事实、助手提议、未知信息分别保存。暂定起点不是“已测得的水平”。
- 先让反馈影响本次教学，再评估通用 skill 的版本升级。
- 知识学习默认以讲述和举例为主，用户主动提问；练习与理解检查仅在用户明确需要时开启，不在每张卡片后要求作答。

## 2. 信息分层：必须清楚什么

| 层级 | 信息 | 为什么需要 | 缺失时处理 |
| --- | --- | --- | --- |
| 核心 | 学习目的：为什么学、希望解决什么 | 决定内容取舍 | 先从用途补问；说不清时提供具体情境帮助选择 |
| 核心 | 本次范围：主要学什么、先不展开什么 | 避免框架过宽 | 提出小范围草案供选择，不要求先懂学科分类 |
| 核心 | 阶段成果：希望能解释、判断、计算或完成什么 | 给路线与后续检查提供锚点 | 提出可执行成果，注明是建议，不冒充用户原话 |
| 条件性 | 已有基础与相关经历 | 决定起点和前置内容 | 经历与理解分开；可采用可调整起点或短体验 |
| 条件性 | 截止日期、指定教材、考试或任务要求 | 可能直接改变路线 | 本次出现明确约束时，提升为开始前需要解决的缺口 |
| 辅助 | 时长、表达方式、例子偏好、详细程度 | 调整节奏和卡片 | 允许留空，使用已展示且可改的暂定安排 |

“必须清楚”指能做出合理的下一步决定，不要求答案精确到永久不变。核心项可以是用户明确表达，也可以是已展示、可修改的助手提议。后者必须持续标记为 proposed。

**阻塞缺口**：不同答案会改变首段学习的内容或顺序，且无法提出合理的小范围起点。只有这类缺口阻止继续。未知基础本身不自动阻塞；用户要求直接学习高级内容且前置不足可能造成明显断层时，简短询问相关接触经历或提供带前置解释的试读。答题式诊断需用户明确需要后再开展。

## 3. 每轮怎么问

### 3.1 固定处理顺序

1. 先读取本次原话、已有草案和相关有效记忆；本次明确纠正优先。
2. 提取所有已经回答的信息，不重复询问；复合回答可以同时更新多项。
3. 标记未知、冲突和助手提议，判断是否存在阻塞缺口。
4. 选一个最影响下一步的缺口，只问一个主要问题；若已足够，直接展示约定。
5. 保存结果后展示；等待用户新输入，不自行模拟用户回答继续循环。

问题优先级通常为：目的 → 范围/主次 → 阶段成果 → 影响首段内容的约束 → 起点 → 辅助偏好。已经明确的项目跳过，不机械按顺序问满。

### 3.2 交互规范

- 开场允许自由描述；补问默认 2—4 个简短选项，不为凑数量编选项。
- 提问默认用一两句短话说清，一次只问一个主要问题。能直接问就直接问，不在每轮重复目标、铺垫或解释整段路线；选项只在能降低回答负担时提供。
- 当术语需要解释、问题容易误解，或答案会明显改变学习安排时，允许增加必要说明；先给核心问题，再补最少背景。简短是默认，不设影响准确性和理解的硬字数上限。
- 单选用于“现在优先做哪件事”；多选用于兴趣、用途和偏好。
- 自由输入始终可用，允许“选 B，同时补充一句”，无需先选“其他”。
- 在适合的题目中提供“不确定，先体验”或“暂时跳过”；固定约束确有必要时解释原因并提供缩小范围的替代方案。
- 接受自然语言的多选与侧重。只有主次会影响有限时间内的取舍时，才继续询问优先级。
- 必要时简短解释这次回答如何影响安排，不要求每轮都解释；不要把内部字段、skill 名称展示给学习用户。
- 对愿意多说的人先提取后补问；对简短回答提供轻量选项。不把字数少、漏答认定为不积极。

### 3.3 漏答与纠正

| 情况 | 正确行为 | 错误行为 |
| --- | --- | --- |
| 问基础和经历，只回答经历 | 保存经历，基础继续未知；按必要性决定是否追问 | 没做过就认定零基础 |
| 两项都选，有偏重 | 主线记录偏重方向，另一项保留为兴趣或支线 | 强迫只选一个或平均分配 |
| 用户不能自评基础 | 提供带解释的小例子或短试读，依据用户自愿反馈调整，未验证的基础仍为未知 | 反复追问自评题或未经选择就加入测验 |
| 用户纠正旧信息 | 更新当前字段，保留替代关系和来源 | 把旧记忆与新回答拼成事实 |
| 用户要求开始，辅助信息缺失 | 用明确标注的暂定安排继续 | 要求填完所有问题 |

### 3.4 学习阶段的提问边界（本次试用修订）

默认采用“是什么 → 用途 → 简单例子 → 必要条件与局限”的讲述方式，按内容需要组合，不机械要求每页包含全部步骤。提问入口持续可用，用户可以直接继续阅读。

- 需求补问用于选择路线；知识提问、练习和测评属于另一类交互，不能因完成访谈就默认开启。
- 卡片不默认附带要求作答的思考题，不每页询问“懂了吗”，也不以回答正确作为翻页或继续学习条件。
- 示例直接展示解释与计算过程，帮助理解，不自动把示例变成考题。
- 用户明确要求练习、测验或答题式检查时再开启；备考目标也不自动等于同意每页作答。允许随时退出练习。
- 用户主动提问、说太难或太简单、纠正解释时，利用这些具体反馈调整。没有反馈只保存浏览进度，理解和掌握仍未知。

后续已选定的交互：首次完成节点浏览即点亮知识树；用户从节点详情主动进入独立的“加强学习”，通过后获得橙色掌握标记；取消自评掌握。加强学习不打断主线、不作为继续条件。详细规则及卡片生成草案见[《知枝-卡片阅读与加强学习设计》](/workspace/三创赛知枝/outputs/知枝-卡片阅读与加强学习设计.md)。

## 4. 阶段状态与结束条件

| 状态 | 含义 | 合法下一步 |
| --- | --- | --- |
| collecting | 自由表达或仍有关键缺口 | 单个补问；或生成约定草案 |
| agreement_draft | 核心项有可执行草案，已向用户展示 | 用户修改；继续框架草案；或确认约定 |
| handed_off | 程序已保存交接快照 | 下一阶段读取该快照；必要时返回修订 |

另设 agreement_status：draft / accepted。阶段交接与用户认可程度分别记录。

**产生可交接草案的条件：**目的、范围、阶段成果均有具体值；无阻塞缺口；起点有可调整方案；未知项和提议仍可识别。空泛的“学好”“精通”不能直接通过，要转成第一阶段可观察的成果。

**如何结束：**展示两三句话的学习约定，并提供“按此继续”和“修改”入口。自然语言“就这样，开始吧”同样有效。用户没有回应不是认可；不要因等待时间到而写入 accepted。

无需每个字段都单独确认。如果用户在看过草案后明确要求继续，接受的是当前展示的总体约定，不会把未知基础变成已确认事实。接受范围记录到具体 revision。

用户要求“先给我看路线”时可交接 draft 快照，下一阶段只展示框架草案，保留修改入口，不宣称最终约定已经确认。若用户直接说“先让我体验”，可进入明确标记的试读，不将其当作正式整门课已建立。

**第一阶段完成标准：**一份已保存、可修改、能指导框架生成的学习约定及交接快照。第一阶段不负责证明用户掌握知识，不负责完成全量检索，也不要求生成正式课程和首批卡片。

## 5. 最小数据契约

下面字段是知枝拟定的业务契约，不是 Pi 的内置 API。字段使用同一结构：

```json
{
  "value": null,
  "status": "unknown",
  "evidence_ids": [],
  "reason": "尚未询问或尚未回答"
}
```

status 仅为 explicit（用户明确表达）、proposed（助手提议）、unknown（未知）、conflict（冲突待处理）。不将它与知识掌握程度混用。证据 ID 由程序分配，必须指向实际存在的消息或学习事件，不能由模型创造来源。

最小记录结构如下；为简洁起见未填写所有可选字段：

```json
{
  "schema_version": "intake-1",
  "intake_id": "intake-example",
  "revision": 1,
  "stage": "collecting",
  "agreement_status": "draft",
  "accepted_revision": null,
  "fields": {
    "purpose": {"value": null, "status": "unknown", "evidence_ids": []},
    "scope": {"value": null, "status": "unknown", "evidence_ids": []},
    "outcome": {"value": null, "status": "unknown", "evidence_ids": []},
    "baseline": {"value": null, "status": "unknown", "evidence_ids": []},
    "experience": {"value": null, "status": "unknown", "evidence_ids": []},
    "constraints": {"value": null, "status": "unknown", "evidence_ids": []},
    "preferences": {"value": null, "status": "unknown", "evidence_ids": []}
  },
  "blocking_gaps": [],
  "deferred_gaps": [],
  "start_plan": null,
  "summary": "",
  "next_action": "ask_one_question"
}
```

范围或偏好有多项时，value 可以保存结构化主次，例如 {"primary":"长期投资","secondary":["短期交易"]}。每个字段的具体 value 类型由开发时的 schema 固定，不允许运行中任意混用字符串与对象。

每轮模型返回一个业务结果信封：reply（展示文本）、question（可空；含单/多选模式、选项及自由输入标志）、field_updates、blocking_gaps、deferred_gaps、start_plan、next_action。模型只建议更新；ID、revision、accepted_revision 和实际交接由程序维护。最多一个主要 question；next_action 从 ask_one_question / offer_trial / show_agreement / propose_handoff 中选择。

agreement 被修订后增加 revision，旧 accepted_revision 保留作历史，新版仍为 draft，直到用户明确接受对应内容。不因修改表达偏好而重新询问全部需求。

## 6. A 股模拟复盘：实际应该交出什么

| 项目 | 应记录的内容 | 状态 |
| --- | --- | --- |
| 目的 | 希望自己做投资决策 | explicit |
| 范围 | A 股；偏重长期，兼有短期兴趣 | explicit |
| 宽泛成果 | 看懂股票基础、理解市场逻辑、形成自己的策略 | explicit |
| 第一阶段成果建议 | 能解释股票权益与交易基础，并说明公司、价格和风险之间的基本区别 | proposed，需展示后才能决定采用 |
| 经历 | 已开户，未买过股票 | explicit |
| 理论基础 | 没有回答概念理解问题 | unknown |
| 节奏 | 每天一小段 | explicit，不擅自换算成十分钟 |
| 表达方式 | 未明确 | unknown |
| 起点方案 | 先看一张带解释与数字例子的入门试读；依据用户自愿反馈调整，不默认提问测验 | proposed |

“只能买 A 股”保留为用户当时表达，不扩写成经核实的账户权限或市场准入事实。学习模拟信息默认属于本次学习情境，不直接创建全局个人事实。

此时不必继续追问投资金额等与第一段学习无关的信息。应展示具体的阶段成果建议和起点，允许修改后进入下一阶段。此前直接跳到卡片的模拟，是试读路径，不能作为已经完成正式框架与检索的证据。

## 7. Pi 如何承载这一阶段

### 7.1 架构与职责

```text
界面：自由输入、选项与补充、约定确认/修改
    ↓
知枝业务层：读取状态 → 准备阶段上下文 → 校验输出 → 保存与切换
    ↓
单一学习 Agent：显式装入需求分析规则，按需补学科规则
    ↓
Pi Agent Core：执行模型与工具循环，产生运行事件
    ↓
模型适配器 / 业务工具 / 本地持久化
```

Pi Core 提供 Agent、工具执行和事件机制；完整 SDK 的官方嵌入环境为 Node.js/Bun。当前手机独立运行目标下，优先做 Core 适配验证，而非直接引入完整 SDK。依据见文末官方文档。

Core 的使用不等于自动具备完整 SDK 的资源发现、skills 加载和会话持久化。知枝显式加载内置规则，维护学习状态与必要会话。教学阶段不能仅依赖模型自主选择 skill。

通用需求规则处理信息提取与访谈；学科规则只补充“哪些基础或约束影响起点”；教学方法按需用于试读。不要因为主题是历史或数学，就各复制一整套访谈流程。

### 7.2 MVP 工具与提交边界

第一阶段只需要只读业务工具，例如 get_intake、find_relevant_memory；工具名为本方案建议。最终结构化结果由业务层提交，避免同一轮既由工具写入又由结束事件再次写入。

- 模型调用只读工具可辅助提取，不能自行将记忆推测改成用户事实。
- 原始用户输入先本地保存；模型结果校验通过后再一次性提交草案、回复和交接状态。
- 对同一 intake 的更新串行执行，并检查 expected_revision；旧请求返回时不覆盖新答案。
- 保存使用 request_id 去重，事务成功才显示成功。重试复用同一 request_id；用户新一轮输入使用新 ID。
- 只保存必要的 Pi 消息与已完成结果；未完成工具调用标记中断，不伪造工具成功，也不承诺自动恢复到任意中间步骤。
- 模型请求返回失败时保留已保存原话；格式错误不写入正式草案，提供重试。

建议起始预算：每次用户输入正常只调用一次模型；若发生工具调用或格式修复，总模型请求最多四次、工具调用最多三次，修复最多一次且计入总预算。预算由业务层计数并中止，不依赖模型自觉遵守，也不冒充某个 Pi 同名参数。上限是待试用调整的初始值，不是效果结论。

用户补问一旦形成可展示结果，就结束本次运行等待回答。Pi 内部工具循环与多轮用户访谈是两个不同循环。

### 7.3 当前项目的接入点与技术门槛

| 现有位置 | 建议工作 |
| --- | --- |
| skills/intake.md | 按本文扩充信息分层、漏答、多选、停止与输出规则；实现时再修改 |
| prepare-mobile.py 与 static/skills | 沿用公开规则打包，明确版本；以源码 skills 为维护源，避免手动维护两份 |
| static/mobile-service.js | 拆出需求草案的状态/校验逻辑与运行适配接口，复用 IndexedDB 提交方式 |
| static/app.js | 支持单/多选加自由补充，显示约定与“继续/修改”入口 |
| PersonalPlugin.java | 现有 generate 只接收 system/topic 并提取 message.content；不足以直接承载完整工具协议 |
| server.py | 电脑预览如跟随实现，保持同一业务契约，不要求复用安卓原生存储 |

Pi 技术验证须先锁定依赖版本并实际打包到 Capacitor：验证 WebView 依赖、通过原生网络层传递完整消息和工具定义、工具调用/结果回传、错误取消、重开后恢复已提交草案。密钥继续留在原生安全存储，不为接入把密钥移入普通网页脚本。

需要实现的是 Pi 所需的模型消息与事件适配，不是简单把 content 字符串换个函数名。非流式模型回复能否转换成所需事件也必须实测。桌面 Node 演示通过不代表安卓通过。

若技术验证未通过，先用现有阶段式请求实现同一需求契约，保留之后替换运行内核的接口；不悄悄改为必须依赖云端后端。Pi 仍为候选，不能把本设计文件标记成接入完成。

## 8. 第一阶段的验收清单

下列均为待执行案例，本轮只核对设计覆盖，不宣称已通过模型或真机测试。

| 输入或事件 | 应观察的结果 |
| --- | --- |
| 一段话已说明目标、范围与基础 | 自动提取，不重复询问 |
| 只回答交易经历 | 经历已知，理论基础仍未知 |
| 两种方向都选且有侧重 | 主次保留并影响路线草案 |
| 回答“不知道，先体验” | 提供可调整起点，不强迫自评 |
| 用户选择讲述举例、不想被提问测验 | 直接提供解释与完整例子，允许继续阅读；不把未作答当作未完成，也不认定已掌握 |
| 连续简短回答 | 一轮一个主要问题，选项可直接作答 |
| 用户纠正旧信息 | 本次明确纠正优先，有来源且保留修订 |
| 辅助信息未填，用户想开始 | 核心草案足够即可展示约定与继续入口 |
| 有明确考试日期或指定教材 | 识别为影响安排的约束，不漏掉 |
| 核心成果只是“精通” | 提出具体阶段成果，不直接认为可执行 |
| 未回应约定 | 不写 accepted，不因超时自动认可 |
| 看过草案后说“先给路线看看” | 交接 draft，展示可改框架，不冒充正式确认 |
| 模型生成无来源的基础判断 | 拒绝当作 explicit，保留 proposed 或 unknown |
| 两次请求乱序返回、重复重试 | 不覆盖新 revision，不重复写入 |
| 断网、保存失败、重开应用 | 原话与已提交状态可恢复，未保存不报成功 |

分别用一个数学小主题和一个历史小主题跑通，再用本次 A 股对话做漏答与多选回归。通过依据是行为正确，不只是 JSON 可解析。

## 9. 交给下一阶段的内容

交接一个不可变快照：intake_id、revision、agreement_status、accepted_revision、目的、范围与主次、阶段成果、基础及其证据、约束、偏好、暂定起点、未知项、可用材料引用和规则版本。原始材料未知时留空，不补造来源。

下一阶段为**框架草案与资料计划**：

1. 读取快照，解释为什么这样组织主线。
2. 标出节点目标、前置关系和选学分支，不直接生成整套正文。
3. 列出每个关键节点需要的资料和待核实内容；已有材料先用，没有工具时不能声称已经搜索。
4. 资料检查后局部修订框架。若发现范围过大或目标冲突，只回问相关缺口，保留已有效信息。
5. 保存框架引用的 intake revision；约定变化时标记相关草案待更新，不删除旧学习记录。

继续模拟的下一步，应先给用户看一份可修改的投资学框架草案及其内容依据计划，而不是直接生成更多股票卡片。

## 10. 规则如何更新

本次反馈改变解释；情境偏好写入个人资料；可复现的通用问题进入 skill 改进记录。记录触发原话、旧结果、预期行为和候选改动，以第 8 节案例检查后再版本化发布。

第一版不实现对话后自动重写正式 skill。文档、skill 版本、业务 schema 和模型版本分别记录。已有约定保留所用规则版本；升级后仅在新交互中使用新规则，必要时显式迁移数据。
