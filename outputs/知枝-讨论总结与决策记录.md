**二、项目定位与已有进度**

知枝是私人学习助手：用户自由表达学习需要，系统协助明确目标、建立路线，以短卡片、答疑和学习树推进，并保存学习经历与个人资料。

按[源码说明](/workspace/三创赛知枝/outputs/learning-grove/SOURCE-GUIDE.md)和[安卓推进记录](/workspace/三创赛知枝/outputs/learning-grove/ANDROID-PLAN.md)，当前方向是安卓个人使用、本地存储、用户提供 API Key、手机直连 DeepSeek，无账号及自建服务器要求。电脑版本另有 Python 本地服务。

已有需求整理、路线、卡片、学习树、问答历史、相关记录检索、记忆管理、分支和 JSON 导出。记录显示最小安卓版已做过用户真机验证，0.6.1 完整迁移版已编译及模拟检查，完整真机验收仍待完成。导入恢复、前后台与返回专项适配、诊断导出等尚未完成。

当前四份教学规则是 intake、roadmap、cards、tutor；它们由业务代码调用，不是四个独立 Agent。尚未接入 Pi，也没有完整自主工具调用循环。当前检索主要指本地历史记录检索，不能等同于已具备联网知识检索与来源核验。

**三、原始 skill 构想与补充**

用户最初提出六类 skill，按学习阶段组织。讨论保留这些能力，但调整部分职责：

| 能力 | 原始构想 | 讨论后的职责边界 |
| --- | --- | --- |
| 需求分析 | 反复对谈，明确需要，与框架相互照应 | 信息足够决定下一步就开始；保留未知和暂定项，使用中继续验证 |
| 知识与资源检索 | 检索需要学习的内容 | 与框架相互修订；保存节点对应的资料片段、出处、适用范围和疑点；配合真实工具 |
| 框架生成 | 整理知识与学习线路 | 生成节点目标、前置关系、主线和选学分支，保留稳定节点 ID |
| 卡片生成 | 拆成小块，优化语言，附举例 | 每张卡完成一个小目标；类型和数量依内容决定，避免遗漏必要条件 |
| 个人数据库 | 根据回答和学习内容形成个性化资料 | 程序负责存储；skill 提取候选记忆、检索线索及学习判断，并保留来源与情境 |
| 知识树生成 | 生成结构、画风和外形 | 复用课程框架的节点；程序处理布局、状态和交互，模型可辅助结构建议或样式选择 |

另建议保留独立答疑能力，增加学习检查与回顾。读过、主动完成和有证据表明理解应分别记录。

**四、整体学习流程与循环锚点**

讨论推荐以下流程：

```text
自由表达 → 必要补问 → 学习约定
                         ↓
               草拟框架 ↔ 资料检索与检查
                         ↓
                    初始路线
                         ↓
          首批卡片 → 阅读、提问、可选练习
                         ↓
                    保存学习事件
                         ↓
        继续 / 换讲解 / 检查理解 / 补基础 / 调整路线
                         ↓
                 准备下一小段内容
```

总锚点是学习约定，包括目的、目标程度、已有基础及依据、范围、完成依据和时间等约束。节点还有自己的小目标，说明用户学完后希望能解释、计算、比较或完成什么。目标为了解时，不应自动升级为考试训练。

调整依据有两种：内容依据说明知识来自哪里，学习证据说明用户实际说过什么、做过什么。模型的概括不能替代原始证据。

循环入口是新事件，出口是下一步行动。普通翻页保存进度；明确不懂先处理当前讲解；暴露前置缺口再补基础；改变目的才修订总约定。没有新问题时继续学习，不启动无休止的“全面优化”。改变约定应说明原因并保留版本。

连续两次换解释仍无改善后转为定位卡点，是引用会话提出的初始策略示例，不是已验证的最佳次数，也不是当前实现。

**五、需求访谈模拟中发现的问题**

引用会话以投资学学习为例，模拟了自由表达、确认目标、了解基础、选择范围、安排主线和开始第一张卡片。这只是交互模拟，没有创建真实课程或写入项目数据库。

模拟的主要发现如下：

| 情况 | 暴露的问题 | 归纳出的处理规则 |
| --- | --- | --- |
| 用户只回答经历，没回答概念理解 | 把“未交易”误用成已确认知识基础 | 经历和理论基础分开；漏答保存为未知，必要时用短例子验证 |
| 用户两项都选，但有侧重 | 单选结构无法保留真实意图 | 记录主要目标、次要兴趣和暂未确定项，形成主线与支线 |
| 用户积极性和表达长度不同 | 连续补问或固定问卷容易妨碍开始 | 愿意多说就先提取信息；简短回答提供选项；不确定就先体验 |

需求分析收敛为“自由表达 → 少量选择补问 → 暂定方案 → 学习中验证”。一轮只问一个主要问题，可提供少量选项，始终允许自由补充；选项数量不是硬性要求。

信息保存为用户已明确、尚未确认、系统暂定三种状态。三种状态说明信息来源和当前处理方式，不代表用户自述能力已经客观验证。只追问影响下一步的缺口，并让用户看到回答怎样改变路线。

“足以开始”与“基础已确认”必须区分。第一阶段不以所有字段填满为结束条件。

**六、落地与迭代方式**

讨论比较了一次完成整套逻辑、逐模块做完再整合两种方案，推荐先设计共同数据骨架，再用一个小主题跑通完整学习过程，之后每轮增强一个能力，并重跑整个过程。

共同数据包括学习约定、知识节点、资料依据、卡片、学习事件与证据、个人记忆。应先明确它们的关联，再扩写提示词。

验收重点是：反馈是否影响下一次讲解或内容，改目标是否影响路线，退出是否能继续，而不只是每份 skill 是否能输出一份漂亮的结果。

**七、记忆与 skill 如何持续改进**

记忆分为原始学习记录、个人资料、带证据的学习判断。用户明确表达、操作事实、助手推测应区分；情境不同的偏好可以共存；纠正后旧记录停止作为有效依据，删除范围需明确。

更新分三个层次：

| 层次 | 例子 | 建议处理 |
| --- | --- | --- |
| 当前讲解 | 用户没看懂这个例子 | 当场换讲解，保留对应记录 |
| 个人适配 | 学数学时更喜欢先看图像 | 保存有范围、有来源的个人偏好 |
| 通用规则 | 多次案例都遗漏定义条件 | 形成 skill 修改候选，验证后发版 |

建议使用阶段性规则评估流程：汇总问题 → 判断归属 → 提出最小修改 → 重跑典型案例 → 采用或退回。它可以由同一个 Agent 另一次运行完成，不需要常驻优化 Agent。

修改记录说明问题证据、涉及规则、预期改善、可能副作用和验证结果。个人偏好优先进入个人记忆，事实错误优先修资料和内容；通用 skill 用版本管理保存，保留回退能力。MVP 不做每次对话后自动改写正式 skill。

**八、当前会话补充的运行架构**

用户提出复用 Pi 的运行逻辑，记忆和 skills 按自己的需求设计；不同 Agent 可以复用同一内核。讨论逐步收敛到 MVP 先用一个学习主 Agent，不实现总 Agent 调度子 Agent。

单 Agent 可以使用多份 skills、多次模型调用和多个按任务组织的会话，不等于无限增长的一条聊天记录。Pi 承担通用执行机制；知枝负责教学规则、相关上下文、资料和记忆、业务校验与可靠保存。

Agent Core 是当前安卓独立运行约束下的优先验证候选。完整 Pi SDK 提供更多上层机制，但官方嵌入环境为 Node.js/Bun；Core 不自动提供完整 SDK 的 skills 加载、插件与会话管理。二者的功能边界分别见[Core 文档](https://github.com/earendil-works/pi/blob/main/packages/agent/README.md)和[SDK 文档](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/sdk.md)。

本次查看现有安卓接口发现：请求使用 system/user 文本消息、非流式返回，提取 message.content。它尚未暴露 Agent 工具循环所需的工具定义、工具调用与工具结果传递。因此“通过原生层继续调用模型”仍需适配验证，不能当作已经打通的接入方案。

只有实际出现独立并行检索、后台备课或需要隔离上下文的审核任务时，再评估子 Agent。增加 Agent 数量本身不能保证知识准确。

**九、跨学科 skill 的补充设计**

本轮建议按需组合三层规则：

| 层次 | 负责什么 | 例子 |
| --- | --- | --- |
| 通用流程 skill | 每一阶段做什么、接收与交出什么 | 需求、路线、卡片、答疑、记忆 |
| 学科规则 | 组织、讲解、验证知识时的专业要求 | 数学的条件与推导；历史的史料、背景与解释 |
| 教学方法 | 可复用的讲解与练习方式 | 比较、反例、分步示范、回忆练习 |

学科知识主要通过参考资料提供，不把整门课程写进 SKILL.md。更细的规则只在反复出现特定需求时增加。当前已有 Markdown 教学规则也不能仅因改名就视为已经具备标准 skills 运行机制。

例如：导数卡片使用卡片 skill、数学规则、当前资料和图像讲解方法；工业革命卡片使用同一通用 skill，组合历史规则、相关史料和因果分析方法。跨学科学习可以按节点加载不同规则，不必给整棵树固定唯一学科。

目标与基础仍决定内容深度：看懂变化率和准备高数考试需要不同安排。学科记忆应记录具体表现，避免形成“数学差”“历史好”的永久标签。

**十、引用会话中的协作与环境讨论**

以下为引用会话中讨论过的边界归档，不是本次重新核验所有 Tutti 功能后的能力清单。

| 主题 | 可保留的认识 |
| --- | --- |
| 模型、运行时与 Tutti | 模型、Agent 运行机制与托管协作环境各有职责；切换模型不代表继承本地插件、授权或记忆 |
| 工作区与本机 | 当前工作主要发生在托管 Linux 工作区；不能因为使用某人的模型，就获得其电脑或其他成员电脑的访问能力 |
| 跨环境接续 | 源码、进度、决策与待办可通过文件或 Git 衔接；共享文件不等于完整接管正在运行的会话内部状态 |
| Git 与版本 | Git 是版本管理工具，GitHub 是可选托管平台；保存源码历史与交付可测试包分开处理 |
| 版本隔离 | 新 Agent 会话不自动隔离文件；独立改版需要目录或 worktree 等隔离办法，合并另行处理 |
| 测试包 | 版本号、源码提交、改动说明和已知问题应对应；讨论过的做法不等于已经建立仓库或发布全部版本 |
| 系统与依赖 | 可按需配置依赖，但 Linux 验证不自动替代 Windows 或安卓真机验收；历史环境检查结果可能变化 |
| Godot 与 MCP | 插件文件、编辑器运行、服务连接和项目同步分别处理；本地已配好不代表云端已可使用 |
| 平台未知项 | 新成员历史可见范围、一房一虚拟机、完整快照回滚、本地连接等曾被讨论，但未得到充分核验 |

聊天分享、账号显示、公网出口与数学开放问题属于旁支问答，没有形成知枝的产品需求。
