# 知枝：TypeScript + React 手机运行验证

日期：2026-10-24。范围：独立兼容性样例；正式知枝 1.0.1 没有迁移到 React，也没有修改其学习数据。

## 结论

**TypeScript + React + Capacitor 是知枝可以继续采用的 Android 技术路线。** 本次已实际通过严格类型检查、生产构建、浏览器交互和 Android APK 构建，现有 Pi 运行模块能够与 React 界面一起打包并执行工具循环。

本次结论是“技术路线可行”，尚不足以声称“正式知枝已在目标手机稳定运行”。环境没有可用的安卓真机或模拟器；真实 WebView、原生桥接执行、后台切换、内存与耗电仍待手机验收。没有调用真实模型账户。

## 运行机制与语言影响

```text
TypeScript / TSX 源码
  → 类型检查与生产构建
  → JavaScript + CSS + HTML
  → 打入 APK 的本地资源
  → Android WebView 执行界面与 Pi
  → Capacitor 插件访问必要的原生能力
```

- TS 类型声明在构建时移除，手机无需安装 TS 编译器或 Node.js。运行成本取决于构建得到的 JavaScript 与依赖；不能用“用了 TS”直接推断更快或更慢。
- React 本身增加运行库和渲染工作。组件更新频率、长列表、长正文、图片和任务状态管理会影响运行表现；本样例没有证明完整知识树的性能。
- TS 能提前检查部分接口与数据使用错误，但不能代替模型返回值、导入档案和存储数据的运行时校验，也不能解决断网或后台进程被系统回收。
- 当前样例采用 React Web + Capacitor，界面实际运行于 Android WebView。

依据：[React 官方 TS 文档](https://react.dev/learn/typescript)、[TypeScript 类型移除说明](https://www.typescriptlang.org/docs/handbook/2/basic-types.html#erased-types)、[Vite 类型检查说明](https://vite.dev/guide/features.html#typescript)、[Capacitor Android 文档](https://capacitorjs.com/docs/android)。

浏览器最终完整运行包含 10 项检查，约 8.2 秒完成。机器记录：[browser.json](browser.json)、[apk.json](apk.json)。该时长是自动化脚本耗时，不是手机速度或启动时间。

首轮浏览器检查与资源重建并行执行，在刷新等待处超时；结束构建后完整重跑通过。首次超时未单独确认根因，因此不归因为已定位的 React/TS 缺陷。后续执行顺序固定为“构建完成 → 启动预览 → 浏览器检查”，检查期间不重建资源。

## 手机上还需要验证什么

以下为后续验收步骤，尚未执行：

1. 安装独立验证 APK，冷启动并点击“检查原生桥接”，确认回传正确，记录实际 Android 与 WebView 版本。样例构建目标为 WebView 110；最低 Android SDK 不自动保证旧 WebView 兼容。
2. 保存偏好和阅读位置，退出重开；再执行慢任务、取消、失败后重试和断网下的本地阅读。
3. 前后台切换、锁屏后恢复和系统终止后重开，检查已提交记录；不要求普通 WebView 任务在后台永久运行。
4. 迁移正式业务后，用真实模型和指定教材跑通一个节点，检查网络取消、资料读写和状态一致性。
5. 在目标手机上进行连续学习与大数据量测试，观察卡顿、崩溃、内存和耗电。长期稳定性、低端机与多机型兼容性由这些记录支持。

## 对正式工程的建议

继续采用 React + TS，按界面、业务核心和平台适配分层。将 TS 类型检查独立加入提交检查；模型与档案输入维持运行时校验；任务取消、原子保存、版本冲突与恢复继续由业务层负责。手机验证贯穿迁移，不能等界面全部重写后再开始。
